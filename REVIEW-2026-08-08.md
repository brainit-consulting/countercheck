# Code review — 2026-08-08

Six independent reviewers over the whole repository, one lens each: detection,
CSV import, state and persistence, the React/Next layer, the in-app manual, and
trustworthiness. Every finding was then handed to a separate agent instructed to
refute it.

The run was cut short by a session limit partway through verification, so the
list below is **as raised**, not as confirmed. Two findings were verified
empirically before the cut, and both were real. Treat the rest as leads: each one
names a file and a line, and several are duplicates of each other seen through
different lenses.

**Already fixed** (commit `4851e4e`): the monthly-only schedule guard, currency
missing from every grouping key and from the UI, Reopen writing a state nothing
counted, unvalidated `decide()` arguments, and `money()` throwing on an
unrecognised currency code.

Counts by severity: 
critical 6, high 19, medium 30, low 10 — 65 in total.


## Critical

### "Reopen" writes a fourth state nothing counts — the finding leaves the queue and its money leaves every total

`app/review/[namespace]/[id]/finding-card.tsx:113`

**How it fails.** I ran this against the demo ledger through lib/store.ts directly. Accept the top finding (vendor-spelling-duplicate, £7,420.00), then press Reopen. Measured before Reopen: open 5 (£19,981.25) / accepted 1 (£7,420.00) / rejected 0 — 6 of 6 findings, £27,401.25 of £27,401.25 accounted for. Measured after Reopen: open 5 (£19,981.25) / accepted 0 (£0.00) / rejected 0 (£0.00) — 5 of 6 findings, £19,981.25 of £27,401.25. £7,420.00 vanishes from Open, Confirmed and Dismissed simultaneously. The finding does not return to the queue: `decision === "deferred"` is truthy, so review/page.tsx still files it under "Decided", where the only control is Reopen again. There is no code path that sets `decision` back to undefined, so the finding is permanently unreachable and permanently uncounted. It is chipped `.tag-deferred`, which globals.css:443 paints in the *open* colours — so it reads as open, is filed as decided, and is counted as neither. The largest number on the front page is the one that silently drops.

**Suggested fix.** Treat "deferred" as a reopen, not a decision: in recordDecision, when decision === "deferred", clear `finding.decision`/`decidedBy`/`decidedAt`/`reason` and still append the audit line. Alternatively drop "deferred" from the Decision union entirely and give the Reopen button its own action. Either way, add an invariant test asserting open + accepted + rejected === total and openValue + acceptedValue + rejectedValue === totalValue after any sequence of decisions.

### Every amount in the review UI is stamped with a £ sign regardless of the row's real currency, including the evidence rows

`app/review/[namespace]/[id]/finding-card.tsx:8`

**How it fails.** I imported a two-row CSV with a Currency column reading USD. importCsv parsed both rows as currency "USD" correctly. The rendered card then disagrees with itself: the explanation (from rules.ts, which honours the row) reads "Cascade Freight invoice CF-100 for US$4,200.00 appears 2 times", while the amount-at-stake beside it renders "£4,200.00" and the evidence table renders "£4,200.00". The evidence table is the one surface the product stakes its credibility on — DESIGN.md §10 calls it "a quotation from their own file" and the manual calls it "your data, quoted back to you, unaltered". It is not unaltered; the currency has been changed. DESIGN.md §6.3 states the rule this breaks verbatim: "Currency comes from the row. Invoice.currency is on every row in src/types.ts. Never assume a default, never infer one from the org, never hard-code a symbol." A US or EU user is shown a printable evidence pack that misstates the currency of their own ledger before they take it to a supplier.

**Suggested fix.** Delete the local `gbp` helper. Format from `row.currency` / the finding's rows, and render the currency as the separate `.cc-ccy` code slot DESIGN.md §6.3 specifies (`USD  4,200.00`) rather than a symbol, so mixed-currency exports are legible and the digit column stays aligned.

### "Reopen" never reopens: a deferred finding vanishes from Open, Confirmed and Dismissed alike, taking its money with it

`lib/store.ts:161`

**How it fails.** A reviewer confirms the £12,480 exact-duplicate, then clicks "Reopen" — a mis-click, or because they want a colleague to look again. `act("deferred")` calls `decide(..., "deferred")`, and `recordDecision` sets `finding.decision = "deferred"`. "deferred" is truthy, so `totals()` counts it in none of open / accepted / rejected. On the home page the Open count drops by one, "At stake" drops by £12,480, AND "Confirmed" drops by £12,480 — the money is now in no column at all, while `total`/`totalValue` still include it, so open+accepted+rejected no longer sums to total. On the review page the finding stays in the "Decided" section tagged "deferred" and never returns to the queue. There is no code path anywhere that deletes `finding.decision`, so the finding is unreopenable and a genuine duplicate payment is now invisible in every headline number on both screens.

**Suggested fix.** Treat "deferred" as open in both places that split the list: `const open = ledger.findings.filter((f) => !f.decision || f.decision === "deferred")` in `totals()` and in `app/review/[namespace]/[id]/page.tsx:16-17`. Cleaner still: have `recordDecision` clear the decision fields (`delete finding.decision/decidedBy/decidedAt/reason`) when `decision === "deferred"` while still pushing the audit line, so "Reopen" genuinely returns the card to the queue and the append-only trail records that it was reopened.

### looksLikeRegularSchedule only recognises monthly cadence, so every weekly, fortnightly and twice-monthly contract is accused of being a duplicate

`src/detection/match.ts:95`

**How it fails.** The guard rejects any cadence under 25 days; rekeyedDuplicates accepts any gap up to 21 days. The whole 1-21 day band is unguarded. Verified by running detect(): a weekly £480 cleaning contract (26 identical invoices, 7 days apart, distinct invoice numbers) returns looksLikeRegularSchedule = false and produces 25 findings, all ruleId 'rekeyed-duplicate', all severity 'high': "Rookwood Cleaning was billed £480.00 twice within 7 days under different invoice numbers (RC-W100 and RC-W101). This is the pattern of an invoice entered twice." A fortnightly £2,200 agency contract (12 invoices) produces 11. One supplier billing two sites the same £1,450 monthly fee on the 1st and the 15th produces 23 (gaps alternate 14/16, avg 15). Dropping a single legitimate weekly £275 courier retainer (52 invoices) into the demo ledger takes the report from 6 findings / £27,401.25 to 57 findings / £41,426.25, with rekeyed-duplicate going from 1 to 52. This is precisely the failure mode the README calls the reason the guard exists; the engine.test.ts precision test passes only because the demo ledger contains no sub-monthly recurring contract.

**Suggested fix.** Detect the modal gap rather than assuming monthly. Accept any cadence whose gaps cluster tightly around their own median (e.g. every gap within max(3, 15% of median) of the median, with >= 3 dates), which covers 7, 14, 28, 30 and 91-day cycles alike. Separately, the group-level skip is too coarse for the two-sites case: when a group splits into two interleaved regular series, test each series.

### Currency is never part of any grouping key, so invoices in different currencies are matched as duplicates and their amounts summed as if comparable

`src/detection/rules.ts:35`

**How it fails.** Invoice.currency exists and importCsv populates it, but no rule keys on it. Verified: two Kestrel Logistics invoices, KES-1 for 5610.75 GBP and KES-2 for 5610.75 EUR, five days apart, produce one high-severity finding reading "Kestrel Logistics was billed £5,610.75 twice within 5 days under different invoice numbers" — two genuinely different sums (~£4,800 apart at any real rate) accused of being one payment. Same for exact-duplicate: HAR-4471 for 3280.50 GBP and HAR-4471 for 3280.50 USD collapse into "invoice HAR-4471 for £3,280.50 appears 2 times". The explanation formats with sorted[0].currency, so the reader is shown one currency for a cross-currency pair. amountAtStake then adds raw numbers across currencies into summary.totalAtStake, which app/review/[namespace]/[id]/page.tsx:5-6 renders with a hard-coded GBP formatter. Any UK ledger with EU or US suppliers hits this.

**Suggested fix.** Add currency to every group key (exactDuplicates, rekeyedDuplicates, vendorSpellingDuplicates, amountTranspositions), require currency equality in the unappliedCredits offset test, and either report totalAtStake per currency or refuse to sum across currencies.

`src/import/csv.ts:139`

**How it fails.** Ran this exact file through importCsv (last column is free text, one description carries an inch mark):

### Any upload over 1 MB is killed by Next before stageUpload runs, so the advertised 25 MB limit is unreachable and its error message never shows

`app/actions.ts:50`

**How it fails.** A user uploads a 4 MB Sage export — roughly 30k rows, exactly the "year of a mid-sized ledger" the constant's own comment names as the target case. Next's action handler aborts the request stream at 1 MB with `ApiError(413, "Body exceeded 1 MB limit.")`. `stageUpload` never executes, so neither the size check nor the `{error: …}` return ever happens and `useActionState` gets a rejection instead of state. There is no error.tsx, not-found.tsx or global-error.tsx anywhere under app/ (I checked), so the user sees Next's generic error page with no indication that the file was too big or what to do. The friendly "export a narrower date range" message is dead code for every file that would actually trigger it.

**Suggested fix.** Add `experimental: {serverActions: {bodySizeLimit: '25mb'}}` to next.config.ts so the app's own limit is the binding one, and add an app/error.tsx so a 413 surfaces as something readable. Do not stop at raising the number: at 25 MB the current path holds the file several times over — `await file.text()` (a 25–50 MB string) → `fs.writeFileSync` (another full Buffer) → `readPending` reads it all back — and app/upload/[id]/page.tsx parses the whole CSV twice with both record arrays alive at once (`parseCsvRecords(pending.text)` at line 21 and again inside `importCsv(pending.text)` at line 26). Stream the upload to disk in `stageUpload` and parse once before lifting the cap.

### Abandoned uploads are never deleted, contradicting the retention promise the UI makes to the user

`app/actions.ts:96`

**How it fails.** A user picks a 4 MB accounts-payable export, lands on the mapping screen, sees the guess is wrong, and closes the tab (or goes back to /upload and picks a different file, or the import returns `{error: "No rows could be read…"}`). `.data/pending/<uuid>.csv` — every supplier name, invoice number, amount and bank-account last-4 in their ledger — stays on disk forever. The `at` timestamp written into the meta at store.ts:145 is never read by anything, so there is no TTL and no sweeper. Every abandoned attempt leaves another full copy, so the directory grows without bound until the disk fills, and both the /upload page and the help book state in plain English that this data has been discarded when it has not. **Suggested fix.** Sweep PENDING_DIR at the top of `savePending` using the `at` field already being written (delete pairs older than, say, 60 minutes), and call `discardPending(id)` on the `!result.rows.length` error path in `confirmImport` too. If the retention window is deliberately unbounded, change the copy on app/upload/page.tsx and app/help/content.ts to say so.

### The "skipped" count in the ledger name is a count of errors, not of rows, so it cannot be reconciled against the source file

`app/actions.ts:92`

**How it fails.** I imported a 4-line CSV (header + 3 body rows) where one row had a blank supplier, a blank invoice number, an unreadable date and an unreadable amount. Measured: rows imported 2, rows actually lost 1, `result.errors.length` 4. The ledger is therefore named "file.csv — 2 rows, 4 skipped" for a file with 3 body rows — 2 + 4 = 6, which reconciles to nothing. ### Date-order radios never render when the column guess missed a required field, making the CSV impossible to import

`app/upload/[id]/page.tsx:28`

**How it fails.** Upload `Who,Doc,When,Value` with rows like `Acme Ltd,INV-1001,03/04/2026,1200.00`. The trial run's guess cannot map vendorName or invoiceNumber, so importCsv returns early at csv.ts:657 with only "has no column" errors and zero per-row date errors. I ran this: `ambiguousDates` = 0, so `needsDateOrder` is false and the day-first/month-first fieldset is not rendered. The user then fixes the four selects (the entire purpose of this screen) and submits. confirmImport reads `form.get("dateOrder")` as null, so dateOrder is undefined, every `03/04/2026` row is rejected as ambiguous, `result.rows.length` is 0, and the action returns `{error: 'invoiceDate: "03/04/2026" is ambiguous: 3 April 2026 if the file is day-first, 4 March 2026 if it is month-first — set dateOrder to "dmy" or "mdy"'}`. confirmImport returns before any revalidate, so the server component never re-renders and `needsDateOrder` stays false forever. ### Ledger id is interpolated into a filesystem path with no validation, while the sibling pending-id path is validated

`lib/store.ts:47`

**How it fails.** `decide` is a "use server" export, i.e. a public POST endpoint whose arguments are plain strings in the request body — no route matching, no framework normalisation. An unauthenticated caller posts the action with `["demo", "../../../../Users/snake/secret", "k", "accepted"]`. I ran the path math: `path.join(path.join("H:\\master-builds\\01-countercheck\\app\\.data", "uploads"), "../../../../Users/snake/secret.json")` resolves to `H:\master-builds\Users\snake\secret.json` — outside `.data` entirely. `readLedger` then does `fs.existsSync` + `fs.readFileSync` + `JSON.parse` on it. `namespace` is not runtime-checked in `decide` either (TS types are erased), so both path segments are caller-controlled.

The read-out escalation is the review page, which passes the route param straight to `readLedger` after validating only `namespace`. Next decodes dynamic params with `decodeURIComponent` (node_modules/next/dist/shared/lib/router/utils/route-matcher.js) and I grepped all of next/dist/server, next/dist/shared and next/dist/lib for `%2f`/`%2F` handling — there is none. So `GET /review/demo/..%2F..%2F..%2Fsomefile` yields `id === "../../../somefile"` and the page renders that file's `name`, `findings` and `audit` into HTML.

**Suggested fix.** Validate in `filePath` the same way `pendingPath` already does — `if (!UUID.test(id)) throw new Error("not a ledger id")` — since every id `createLedger` mints is a `randomUUID()`. Add runtime validation of `namespace` and `decision` at the top of `decide` rather than relying on the erased TS union, and have `readLedger` return null instead of throwing on a bad id so callers still get `notFound()`.

### Ledger writes are not atomic, and one truncated file takes the whole namespace listing down with no recovery path

`lib/store.ts:55`

**How it fails.** `writeFileSync` opens with 'w', which truncates the target first and then writes — there is no temp file and no rename, so the live ledger is destroyed before the replacement is complete, on every single accept/reject. Kill the process during that window (Ctrl-C in dev, a container restart, a full disk, an SMB hiccup) and `.data/uploads/<id>.json` is left as partial JSON. Two things then break, and the second is the bad one: (a) `readLedger` throws out of `JSON.parse` at line 62, so the review page 500s instead of 404ing; (b) `listLedgers` parses *every* file in the namespace inside a `.map` with no try/catch, so that one corrupt file makes `listLedgers("uploads")` throw and the home page dies — every other upload becomes unreachable through the UI. The demo namespace can be recovered with the reset button; uploads has no recovery path at all, and the decisions plus the audit trail in the damaged ledger are gone with no backup. The window is not small at scale either: the whole ledger (all invoices, all findings, the whole audit array) is re-serialised with `JSON.stringify(ledger, null, 2)` and rewritten synchronously on every click, which for a large import is a multi-megabyte blocking write per decision.

**Suggested fix.** Write to `<id>.json.tmp` then `fs.renameSync` onto the target — rename is atomic on both NTFS and POSIX, so a crash leaves either the old file or the new one, never a torn one. Wrap the `JSON.parse` in `listLedgers` in a try/catch that skips (and logs) unreadable files so a single bad file cannot hide the rest, and have `readLedger` return null rather than throw.

### collapse() keys on the row set alone, so a bank-detail-change finding is silently deleted whenever a duplicate rule covers the same two rows

`src/detection/engine.ts:14`

**How it fails.** bankDetailChanges emits invoiceIds [sorted[i-1].id, row.id] and amountAtStake row.amount; rekeyedDuplicates emits [a.id, b.id] and amountAtStake b.amount. For a consecutive pair these are the same key, the same severity 'high', and the same amountAtStake — so `stronger` is false (it requires a strict >), and ALL_RULES order (rules.ts:224-232) puts rekeyedDuplicates before bankDetailChanges, so the bank finding is dropped. Verified: two Halden Site Services invoices, both £4,150, five days apart, invoice numbers HS-1 and HS-1-A, bankLast4 8842 then 2077, yield exactly one finding — the rekeyed-duplicate. The sentence "Payments moved to a new bank account ending 2077... Confirm the change by phone using a number you already hold, not one from the invoice" never reaches the reviewer. Same loss with exact-duplicate (same invoice number + new account: only the exact-duplicate survives) and with vendor-spelling-duplicate. A re-keyed invoice is a clerical annoyance; a re-keyed invoice paid to a new account is the classic supplier-impersonation pattern, and this collapses the second into the first.

**Suggested fix.** Do not collapse across incompatible rule families. Either include ruleId in the collapse key (accepting two queue items for one row pair), or keep the strongest finding but attach the suppressed ones as secondary notes on the surviving finding so the bank-change sentence and its remediation advice still render. At minimum, exempt bank-detail-change from collapse.

### Amounts in different currencies are added together and the sum is labelled in pounds

**How it fails.** I imported a four-row ledger: two duplicate USD invoices of 4,200.00 and two duplicate JPY invoices of 900,000. ### normaliseVendor strips legal suffixes from any word position, merging unrelated companies into one vendor group for five of the seven rules

`src/detection/match.ts:22`

**How it fails.** The filter is positional-blind, so short words that are real parts of a trading name are deleted. Verified: normaliseVendor("LP Gas Supplies") and normaliseVendor("Gas Supplies Ltd") both return "gas supplies" (similarity 1.0); likewise "AG Foods"/"Foods Ltd" -> "foods" and "SA Recruitment"/"Recruitment Ltd" -> "recruitment". rekeyedDuplicates, amountTranspositions, unappliedCredits, bankDetailChanges and roundNumberOutliers all group on exact normalised equality, so these become one supplier. ### vendorSimilarity 0.86 merges numbered sister entities and directional subsidiaries, which differ by one or two characters by design

`src/detection/match.ts:58`

**How it fails.** Normalised length divides the distance, so any two names of 8+ characters differing by one character score >= 0.875 and merge. Measured with the real function: "Halden Site Services 1" vs "Halden Site Services 2" = 0.9545; "Contract Cleaning North" vs "Contract Cleaning South" = 0.9130; "Anderson Roofing" vs "Andersen Roofing" = 0.9375; "Hanson Plant Hire" vs "Hansen Plant Hire" = 0.9412. These are distinct legal entities, and numbered SPVs billing an identical standard charge with per-entity sequential invoice numbers are exactly the shape vendorSpellingDuplicates keys on (normalised invoice number + amount). Verified: "Halden Site Services 1" and "Halden Site Services 2", both invoice SC-001 for £1,500, produce a high-severity "...paid to two supplier records that look like the same company". In the other direction the same threshold misses real aliases: "St James Group" vs "Saint James Group" = 0.8235 and "J Smith & Sons" vs "John Smith & Sons" = 0.8421 both fall below 0.86 and are never linked.

**Suggested fix.** Treat a digit difference as disqualifying — if the two normalised names differ only in numeric tokens, they are different entities, not two spellings, regardless of edit distance. Consider also refusing a merge when the differing characters form a whole distinct word (north/south, east/west), and computing similarity per token rather than over the whole string so short-word substitutions are not diluted by a long shared prefix.

### A credit note is marked applied whenever the supplier later bills the same amount for anything, so genuinely outstanding credits vanish from the report

`src/detection/rules.ts:157`
